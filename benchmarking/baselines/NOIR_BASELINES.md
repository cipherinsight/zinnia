# Noir baselines for the DS-1000 benchmarking suite

This document covers the handwritten Noir + Barretenberg UltraHonk
baseline for the Zinnia-vs-frameworks comparison. **Scope after the
full roll-out: 133 hand-written cases covering the entire DS-1000
working subset that the halo2 baseline also handles.** A separate
phase will then add a Noir backend to the Zinnia compiler so we can
also generate Noir circuits automatically; that is **step 2** and is
not part of this checkin.

## Tooling

- **Nargo** (Noir compiler / witness generator): `1.0.0-beta.20`.
- **Barretenberg `bb`** (proving / verification backend): `5.0.0-nightly.20260324`.
- Proving system: **UltraHonk** (`bb prove --scheme ultra_honk
  --verifier_target noir-recursive-no-zk`).

## Layout

```
benchmarking/
  noir_fpc/                  # shared Q32 fixed-point library
    Nargo.toml
    src/lib.nr
  ds1000_caseNNNN/
    main.nr                  # the Noir circuit (one per case)
    Prover.toml              # per-case fixture (generated by the runner)
    ...                      # halo2 / SP1 / Risc0 / Cairo files (unchanged)
  run_noir_baselines.py      # the runner; writes noir_baseline_results.json
  NOIR_BASELINES.md          # this file
```

`main.nr` lives directly in the case directory (no `Nargo.toml` or
`src/`). The runner stages each case into a tempdir at run time, copies
`main.nr` to `src/main.nr`, materialises a `Nargo.toml` that pulls in
`noir_fpc` by absolute path, and writes the fixture out as `Prover.toml`.

## Fixed-point convention

Mirrors halo2-graph's `FixedPointChip<F, 32>`:

- **Scale: `Q = 2^32 = 4_294_967_296`.** Floats are encoded as Field
  elements equal to `round(value * Q)`. Negative values use the field's
  natural two's-complement-like wrap (`p - |value*Q|`).
- All `qmul` / `qdiv` calls rescale by `Q` (witnessed quotient + remainder
  pattern).
- Equality on floats uses bracketed tolerance via `q_eq_with_tol(a, b,
  tol)` / `q_close(a, b, tol)`. Default tolerance is `TOL_DEFAULT =
  4_294_967` (= 0.001 * Q). Cases that accumulate Taylor or Newton
  rounding (e.g. cos/sin/sqrt) widen the tolerance at the call site.

### Why projection into `(sign, magnitude)`?

Noir's `Field` has **no native ordering**: `<`, `>`, `min`, `max`, `abs`
do not type-check on `Field`. Any case that needs an order comparison
(argmax, sort, less-than, abs) calls `noir_fpc::to_signed(v)`, which
takes an `unconstrained` hint giving `(sign: bool, magnitude: u128)` and
constrains it via `v == (1 - 2*sign) * magnitude`. The runtime then
compares two `u128`s.

This pattern was the single biggest "Noir surprise" -- once you see it,
the rest of the library follows. Functions like `qmul` and `qdiv` also
use unconstrained quotient hints + a single Field-level reconstruction
assertion.

### Other Noir-specific gotchas

- `i64` exists but `i128` does **not**; for wide signed values we encode
  signed magnitude in `u128` plus a `bool` sign bit. Cast `i64 as Field`
  is rejected; cast `u64 as Field` and `u128 as Field` are allowed.
- `for` loop bounds must be compile-time. Cases that take a runtime
  `bin_size` (`0416`, `0418`) instead assert that the input equals a
  comptime constant, mirroring how a real Noir engineer specialises shapes.
- Comments must be ASCII-only. No `pi/180` -- use `pi/180` or write out
  the constant.
- `unsafe { ... }` blocks need a `// Safety: ...` comment above them
  (Noir warns otherwise).
- `Prover.toml` accepts unquoted negative decimals for `Field` inputs
  (`x = -1000`). Quoted strings only work for non-negative decimal
  integers.

## Adding a new case

1. Create `ds1000_caseNNNN/main.nr`. Top comment must say "DS-1000 case
   NNNN -- Noir baseline" + one-line kernel description + any tolerance /
   skip notes.
2. Mirror the algorithm in `kernel.py` (not Zinnia's lowered IR). Loops
   and helper closures are fine and encouraged.
3. Floats -> `Field` via Q32. Inputs are passed as Q-scaled Field; outputs
   that match Zinnia's `ExposePublicFIR` set are returned `pub`.
4. Register a writer in `WRITERS` in `run_noir_baselines.py` to translate
   the shared `INPUT_BUILDERS` dict into `Prover.toml`. The convention:
   - `_write_floats(path, ("name", values))` for Q-scaled float arrays.
   - Integer arrays go as decimal strings via `_toml_array(_ints(d, k))`.
   - Per-case writers exist for the small irregularities (e.g. 0323's
     scalar `degree`).
5. Run `python3 run_noir_baselines.py --cases NNNN` to validate the case
   compiles, proves, and verifies.

**Outcome (full sweep):**
- 133 cases written, 133 prove + verify OK under UltraHonk, 1 skipped
  (0300, percentile -- needs runtime floor + sort + gather).
- Median `prove_seconds_median`: ~0.07 s.
- Range: 0.03 s for tiny passthroughs to 20.7 s for 0364 (insert into
  Float[100,10] -> Float[101,10] expands to a 6.6 M-gate gather).
- Other slow outliers: 0381/0382/0383 (Float[100] selection sort,
  ~2.3 s, 560 k gates) and 0329/0330 (Float[8,6] iterative squaring,
  ~1.3 s, 320 k gates).
- The 20000-cell reshape kernels (0385/0387/0388/0390) are dominated
  by `nargo execute` (witness generation on ~40k Q32 inputs) rather
  than `bb prove` (each only ~40 k gates, ~0.4 s).

The biggest cost drivers are (a) selection-sort networks for argsort /
ecdf and (b) the dynamic-output cases that compile into N^2 compaction
gathers (0442, 0443, 0444, 0462, 0463, 0481). Both shapes mirror the
halo2 baseline's structural choices and so stay apples-to-apples; we
don't try to optimise them away.

## Tolerance + accuracy notes

- 0428 (mean +/- 3 sigma) uses `qsqrt` which is implemented as Newton
  iteration with a witnessed initial guess and bracket constraint `y^2
  <= x*Q < (y+1)^2`. This is exact up to the last unit in the Q32
  encoding; downstream comparisons should still use the default
  tolerance.
- 0323 (sin via Taylor) accumulates polynomial residual; for sin(60deg)
  the 4-term Taylor at `pi/3` is accurate to roughly 1e-3, so external
  consumers should compare with `tol >= 4_294_967` (i.e. `TOL_DEFAULT`).
- 0329/0330 use iterative squaring with a 32-bit loop. For the DS-1000
  sample (`power=3`) this is faithful; for runtime `power > 2^32` the
  circuit would silently truncate. Not a concern for any current
  fixture.

## Runner contract

`run_noir_baselines.py` writes `noir_baseline_results.json` with one
entry per case:

```json
{
  "case": "0334",
  "status": "ok",
  "first_prove_s": 0.113,
  "warm_prove_times_s": [0.108, 0.094],
  "prove_seconds_median": 0.101,
  "nargo_execute_s": 0.18,
  "verify_ok": true,
  "verify_time_s": 0.009,
  "gate_count": 6500,
  "proof_bytes": 13120,
  "vk_bytes": 3680,
  "error": null
}
```

`prove_seconds_median` is the apples-to-apples comparison point against
Zinnia's `prove_seconds` field in `zinnia_halo2_results.json`. The
verifier key is precomputed once with `bb write_vk` before the prove
loop, so subprocess wall-clock around `bb prove ... -k vk` measures the
prover only (excluding VK computation).

`status` values:
- `ok` -- prove + verify succeeded.
- `nargo_execute_failed` -- witness generation failed.
- `vk_failed` -- `bb write_vk` failed.
- `prove_failed_on_iter_<i>` -- proof failed on the `i`-th iteration.
- `verify_failed` -- verifier rejected.
- `missing` -- `main.nr` not found.
- `input_error` -- writer crashed (typo in INPUT_BUILDERS structure).
- `skipped: <reason>` -- intentional skip.

## Step 2 (not in this checkin)

Once the handwritten baselines are stable, the next step is to **add
Noir as a backend in the Zinnia compiler** so we can compile the same
kernel IR to a `.nr` file mechanically. The expected output shape is:

- Zinnia emits one `main.nr` per kernel by walking the IR (similar to
  the existing halo2 emitter under `src/prove/halo2/`).
- The emitted code uses the same `noir_fpc` library this directory
  provides.
- The runner gains a `--zinnia` flag that calls Zinnia's emitter instead
  of reading the handwritten `main.nr`, so we can produce the
  Zinnia-vs-Noir prove-time comparison automatically.

This is a separate engineering task and not part of the current scope.
