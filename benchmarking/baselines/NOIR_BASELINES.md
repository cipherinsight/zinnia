# Noir baselines

The handwritten Noir circuits of the DS-1000 performance set
(`datasets/ds1000/<case>/main.nr`). The rules every baseline follows are in
`CONVENTIONS.md`; this file covers what is specific to Noir.

## Toolchain and proof system

- Nargo `1.0.0-beta.20` (`~/.nargo/bin/nargo`), Barretenberg `bb`
  `5.0.0-nightly.20260324` (`~/.bb/bb`).
- `noir-execute`, Noir's artifact executor, built from the commit nargo reports
  (`python -m benchmarking.harness build --skip-zinnia --noir-execute`, installed
  at `target/noir-execute/bin/noir-execute`). The benchmark harness times it as
  the witness step of both Noir sides.
- UltraHonk with `--verifier_target noir-recursive`: zero-knowledge, Poseidon2
  transcript. The author decided that Noir proofs are zero-knowledge on both
  sides; the June runs used `noir-recursive-no-zk` on both (audit H-08), and
  Zinnia's Noir driver still passes it at this commit
  (`src/prove/noir/driver.rs`), which the compiler side has to change for the
  comparison to be like for like.

## The program: `hw_check.noir_driver`

```bash
cd benchmarking/baselines
python -m hw_check.noir_driver setup  --case ../datasets/ds1000/ds1000_case0309 --workdir W
python -m hw_check.noir_driver prove  --case ../datasets/ds1000/ds1000_case0309 --workdir W --input B
python -m hw_check.noir_driver verify --case ../datasets/ds1000/ds1000_case0309 --workdir W [--tamper-index 0]
```

- `setup` stages a Nargo package under `W/pkg` (`src/main.nr` copied from the
  case, a `Nargo.toml` depending on `baselines/noir_hw`), runs
  `nargo compile`, `bb write_vk` and `bb gates`. Nothing in it depends on the
  input.
- `prove` writes `Prover.toml` for the requested input from `fixture.json`
  (`hw_check.prover_toml`), solves the witness with `nargo execute`, proves with
  `bb prove`, and decodes the public outputs from bb's `public_inputs` file using
  the `// @outputs:` line of `main.nr`.
- `verify` runs `bb verify` on the stored proof, optionally after adding 1 to one
  public value (the tamper test: the run must report `verified: false`).

Each run prints one JSON object (`ok`, `publics`, `proof_path`, `gates`,
`timings_s` with `compile_s`, `write_vk_s`, `gates_s`, `write_inputs_s`,
`execute_s`, `prove_s`, `verify_s`), and exits non-zero when `ok` is false. The
timings are wall-clock times of the subprocesses. The driver is the checking
tool; the benchmark harness does not time it. The harness drives the tools
itself, the same way for Zinnia's Noir output (`harness/adapters/noir_toolchain.py`):
its witness step is `noir-execute` on the compiled artifact, with `nargo execute`
run alongside for the record and required to give the same witness
(`benchmarking/README.md`, section Noir).

`Prover.toml` in each case folder is `prove`'s input file for input B,
regenerated by `python -m hw_check.prover_toml <case dir>`. The writer reads the
compiled ABI, so a parameter may be declared flat (`[Field; 48]`), nested, as a
native integer or as `bool`; floats become `round(v * 2^32)`.

## Writing a baseline

- Parameters carry the kernel's names. Values are `Field`s holding Q32 floats
  and plain integers, as in Zinnia; outputs are returned `pub`.
- The header carries `// @outputs:` (format in `CONVENTIONS.md` section 6).
- Use `noir_hw` for anything that needs an order, a rescale or a quotient:
  - comparisons: `let w = window(x);` once per value, then compare the `u64`
    windows (a 64-bit range check per value instead of `noir_fpc`'s two 126-bit
    projections per comparison; 3,495 vs 7,612 gates on the 48-element argmax);
  - products: `mul` (or accumulate `a * b` and `rescale` once for a dot
    product); `noir_hw::mul` is 3,255 gates for 48 products against
    `noir_fpc::qmul`'s 7,742, with the same rounding;
  - quotients: `div`, `divmod_pos`; casts `to_int`, `from_int`, `floor`;
    `sqrt`, `sin`, `cos`;
  - indexing: `a[index_pos::<8>(i, len)]` (native dynamic indexing, NumPy wrap
    and bounds; `array_index::<8>(k, len - 1)` for a position read from a hint;
    `::<28>` above 128 elements), or `pick(row, i)` for rows of up to 8 values
    (a one-hot over the valid index values, cheaper there: 2,400 vs 7,001 gates
    for 169 length-2 gathers);
  - masked selections (`x[mask]`, `nonzero`, `argwhere`): `select_kept`, or
    `compact` / `compact_rows` for other payloads (a running one-hot of the next
    free slot: 807 gates for 0442 against 7,346 with conditional native writes);
  - constant divisors that are powers of two: `floor_div_pow2`; integer roots:
    `isqrt`; the maximum or minimum of a few values: `max_of`;
  - unconstrained computation checked by constraints when that is cheaper than
    computing in-circuit (sorting: compute the order unconstrained, then check
    the keys read through it strictly increase, as in 0381).
- Range checks are `x.assert_max_bit_size::<N>()` on the original `Field`; an
  `as u64`/`as u32` cast truncates and proves nothing, so it only follows such a
  check (as in `window` and `array_index`). Every `unsafe` hint is followed by the
  checks that pin it, under a `// Safety:` comment.
- `noir_hw` has `nargo test` coverage, including `should_fail` tests that load
  neighbouring or non-integer quotients, wrong square roots and parities, and
  out-of-range indices.

Noir gotchas that matter here:

- The compiler can drop a range check of a value used directly as a memory
  index (it leaves the bound to Barretenberg's memory check), and the pinned bb
  admits a read at index p - 1. Index checks therefore go on derived values:
  `array_index` checks `2 k` and `last - k` (the 7- and 8-bit checks of the
  sort indices in 0381/0383 and 0300 did not reach the circuit;
  `nargo info --print-acir` shows which `RANGE` opcodes survive).
- Barretenberg builds a range table for each bit width a circuit range-checks:
  the first check of any width adds about 2,780 gates, each further width a few
  hundred more. Keep to 32- and 64-bit checks (and 8 or 28 bits: a 64-bit
  check is 14-bit limbs and one 8-bit limb), and prefer one-hot selections
  over indices built from loop constants, which need none.
- `Field` has no ordering; integer types do (after a range check, see above).
- `i64` exists but `i64 as Field` is rejected; keep signed values in `Field` and
  order them through `window`.
- Loop bounds are compile-time constants; data-dependent work goes through
  `if` with native indexing.
- Comments must be ASCII.

## Constraint-free circuits

For circuits with no ACIR opcodes and no public parameters or return values,
Noir can retain unused private ABI inputs in the executor's witness map while
bb expects one unused witness slot. Both benchmark Noir adapters and the baseline
driver use `benchmarking.noir_witness` to supply that zero slot in a separate
transport file; the original executor witnesses remain available for comparison.
Zinnia's standalone Noir driver applies the same rule. No constraints, public
values, input-domain guards, or benchmark-program work are added. In particular,
never expose a private input or add artificial work to make an empty circuit prove.
