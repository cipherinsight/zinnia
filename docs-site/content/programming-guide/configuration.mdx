# Configuration

The compiler's behavior is controlled through `ZinniaConfig`, which sets the compile
target, the unrolling limits, and the optimization passes.

## Imports

```python
from zinnia import ZinniaConfig
from zinnia.config import OptimizationConfig
```

## ZinniaConfig

`ZinniaConfig` is the top-level configuration object. Pass it when creating a circuit:

```python
from zinnia import ZKCircuit, ZinniaConfig

config = ZinniaConfig(
    backend=ZinniaConfig.BACKEND_HALO2,
    recursion_limit=16,
    loop_limit=1000,
    enable_memory_consistency=False,
)

circuit = ZKCircuit.from_method(my_func, config=config)
```

### Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `backend` | `str` | `"halo2"` | Compile target (see below). |
| `recursion_limit` | `int` | `16` | Maximum nesting depth of chip calls. |
| `loop_limit` | `int` | `1000` | Maximum number of unrolled iterations of a `while` loop. |
| `optimization_config` | `OptimizationConfig` or `dict` | `OptimizationConfig()` | Compiler optimization passes. |
| `enable_memory_consistency` | `bool` | `False` | Check the runtime shapes of dynamic-array inputs against their declared bounds. |

An invalid value (an unknown target, or a limit that is not a positive integer) raises
`ValueError`.

## Compile Target

The `backend` option selects the proof system the compiled program is lowered for. It is
separate from the `backend` argument of `prove()`, which selects the prover that runs (see
[Execution and Proving](/docs/programming-guide/execution)).

| Constant | Value | Lowering target |
|----------|-------|-----------------|
| `ZinniaConfig.BACKEND_HALO2` | `"halo2"` | halo2-base. The default. |
| `ZinniaConfig.BACKEND_NOIR` | `"noir"` | Noir. |
| `ZinniaConfig.BACKEND_CIRCOM` | `"circom"` | Accepted and lowered as for halo2-base. |
| `ZinniaConfig.BACKEND_CIRC_ZOK` | `"circ_zok"` | Accepted and lowered as for halo2-base. |

Some array operations are lowered differently for the two targets, so compile with
`backend="noir"` when you will prove with the Noir backend and with the default when you
will prove with halo2-base. Mock execution works with either.

```python
noir_config = ZinniaConfig(backend=ZinniaConfig.BACKEND_NOIR)
```

## Recursion and Loop Limits

A circuit is a fixed system of constraints, so the compiler unrolls every loop and inlines
every chip call. Two limits stop this unrolling when the compiler cannot show that it ends.

- **`recursion_limit`** bounds the nesting depth of chip calls. A recursive call is
  unrolled until the compiler proves the condition under which it is reached false. A call
  still reachable at this depth is rejected with a `ZinniaException` whose message starts
  with `RecursionLimitExceededError` and names the chip. The default (16) is small because
  a branching recursion such as `fibo(n - 1) + fibo(n - 2)` grows as `2**depth`. Raise it
  for programs with deeper bounded recursion.
- **`loop_limit`** bounds the unrolling of `while` loops. The compiler unrolls a `while`
  loop until it proves the loop condition false. If that does not happen within
  `loop_limit` iterations, compilation fails and the message suggests bounding the values
  the condition depends on (with a bounded array annotation or a `requires` precondition)
  or raising the limit. A `for` loop over a `range` or sequence whose length is known at
  compile time is unrolled completely and is not subject to this limit.

```python
config = ZinniaConfig(
    recursion_limit=64,
    loop_limit=5000,
)
```

Higher limits allow larger programs to compile, and the unrolled code makes the circuit
correspondingly larger.

## OptimizationConfig

`OptimizationConfig` controls which optimization passes run during compilation. All are
enabled by default.

```python
from zinnia.config import OptimizationConfig

opt = OptimizationConfig(
    always_satisfied_elimination=True,
    constant_fold=True,
    dead_code_elimination=True,
    duplicate_code_elimination=True,
    shortcut_optimization=True,
)

config = ZinniaConfig(optimization_config=opt)
```

| Option | Default | Description |
|--------|---------|-------------|
| `always_satisfied_elimination` | `True` | Removes assertions that always hold, such as `assert x == x`. |
| `constant_fold` | `True` | Evaluates operations on constant operands at compile time. |
| `dead_code_elimination` | `True` | Removes IR statements whose results are never used by a constraint or output. |
| `duplicate_code_elimination` | `True` | Merges identical computations so they are constrained once. |
| `shortcut_optimization` | `True` | Applies algebraic simplifications, such as replacing `x * 1` with `x`. |

To disable a pass, for example while debugging:

```python
config = ZinniaConfig(optimization_config=OptimizationConfig(constant_fold=False))
```

`ZinniaConfig` also accepts a dictionary in place of the `OptimizationConfig` object. The
dictionary must give all five options:

```python
config = ZinniaConfig(optimization_config={
    "always_satisfied_elimination": True,
    "constant_fold": False,
    "dead_code_elimination": True,
    "duplicate_code_elimination": True,
    "shortcut_optimization": True,
})
```

## Dynamic-Array Shape Checks

A bounded dynamic array input (see
[Bounded Dynamic Arrays](/docs/data-analytics/bounded-dynamic-arrays)) carries its runtime
shape as witness values. The compiler adds constraints checking that shape against the
declared bounds whenever the circuit has such an input. Setting
`enable_memory_consistency=True` enables these checks for every circuit.

## Configuration with Decorators

`@zk_circuit` accepts a configuration as a keyword argument:

```python
from zinnia import zk_circuit, ZinniaConfig, Integer, Private

@zk_circuit(config=ZinniaConfig(loop_limit=5000))
def my_circuit(a: Private[Integer]):
    total = 0
    i = 0
    while i < 2000:
        total = total + a
        i = i + 1
    assert total == a * 2000
```

`ZKCircuit.from_method`, `ZKCircuit.from_source` and the `ZKCircuit` constructor take the
same `config` argument.
