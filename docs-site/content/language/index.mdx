# Language Overview

Zinnia compiles a subset of Python and NumPy to zk-SNARK circuits. A circuit is an ordinary
Python function decorated with `@zk_circuit`. Its parameters are the circuit inputs, its
`assert` statements become constraints, and its return value becomes the public output of
the proof. Because the source is valid Python, the same function can be run with CPython
and NumPy (without the decorator) to test it before it is compiled.

## Design Goals

- **Python compatibility.** Every Zinnia program is syntactically valid Python, and the
  compiler follows Python and NumPy semantics for the constructs it accepts. Constructs it
  cannot represent faithfully are rejected at compile time.

- **Familiar idioms for privacy and constraints.** Inputs are marked public or private with
  type hints (`Public[...]`, `Private[...]`), and constraints are written as `assert`
  statements.

- **Array programming.** NumPy arrays, broadcasting, slicing, reductions and a large part of
  the `np` namespace are available inside circuits, so linear algebra, statistics and data
  transformations can be written as they would be in NumPy.

- **Loops without explicit bounds.** Every loop and recursive call is unrolled at compile
  time. When the number of iterations depends on a runtime value, the compiler proves an
  upper bound from constants, value ranges, preconditions and, when needed, an SMT solver
  (Z3). A program for which no bound can be proved is rejected.

- **Data-dependent control flow.** An `if` whose condition depends on an input is compiled
  by evaluating both branches and selecting the results with the condition, so the circuit
  structure does not depend on which branch is taken.

## A Minimal Example

```python
from zinnia import zk_circuit, Public, Private, Integer

@zk_circuit
def excess(balance: Public[Integer], threshold: Private[Integer]) -> Integer:
    if balance > threshold:
        result = balance - threshold
    else:
        result = 0
    return result

excess(10, 3)   # runs the circuit on the mock backend
```

The circuit takes a public balance and a private threshold and returns the excess above
the threshold (or zero). Both branches are compiled into the circuit and the comparison
selects which value is returned. A circuit may not be named `main`.

## What Zinnia Supports

- Scalar types: integers, floats (fixed point), booleans and complex numbers
- Composite types: lists, tuples, fixed-shape N-dimensional arrays (`NDArray`) and
  bounded-dynamic arrays (`DynamicNDArray`), whose shape is a runtime value below a
  compile-time bound
- Control flow: `if`/`elif`/`else`, `while`, `for`, `break`, `continue`, early `return`
- Helper functions (`@zk_chip`), including bounded recursion, local `def`s and lambdas
- Calls to Python functions outside the circuit (`@zk_external`)
- Privacy annotations via `Public[T]` and `Private[T]` type hints
- Preconditions on inputs (`@zk_circuit(requires=[...])` or `@requires(...)`)
- Assertions that compile to circuit constraints
- A large part of NumPy's array API (see [NumPy API](/docs/programming-guide/numpy-api))
- Inputs committed with a Poseidon hash (`PoseidonHashed[T]`)

## What Zinnia Does Not Support

Because every program must compile to a finite circuit, some Python features are rejected:

- Loops and recursion for which the compiler cannot prove a static bound
- Dictionaries and sets
- Classes
- `try`/`except` (a `raise` statement is accepted and compiles to a failing assertion on
  the path that reaches it)
- File I/O, networking and other side effects
- Imports of modules other than `numpy` and `math` (including their submodules, such as
  `numpy.linalg`)

## How Compilation Works

1. The Python front end rewrites the source (resolving imports, inlining module-level
   constants, turning local functions and lambdas into chips) and translates the function's
   AST into a form the Rust core reads.
2. The Rust core executes the program symbolically: loops and calls are unrolled, branches
   are merged with selects, and every operation is recorded in an intermediate
   representation (IR).
3. Optimization passes (constant folding, dead-code elimination, duplicate-code
   elimination, removal of assertions proved to hold) simplify the IR, and array operations
   are lowered to constructions suited to the target backend.
4. A backend turns the IR into a circuit: the `mock` backend checks the constraints
   directly, `halo2-base` produces a Halo2 proof, and `noir` emits a Noir program and proves
   it with `nargo` and `bb`.
