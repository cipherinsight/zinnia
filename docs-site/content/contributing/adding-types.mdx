# Adding Types

A type in Zinnia exists in several places at once: a name the user writes in an annotation, a type dictionary the AST transformer produces, a `ZinniaType` and a `Value` variant in the core, a way to read it as a circuit input, a way to merge two values of it at a branch, and the operations defined on it. This guide lists those places in order. The complex number type (`Complex`) was added this way and is the reference: searching for `Complex` in `zinnia/` and `src/` shows every case below.

See [Types and Values](/docs/compiler-internals/type-inference) for how the core uses types.

## 1. The Annotation Name

User-facing type names are defined in `zinnia/lang/type.py` and exported from `zinnia/__init__.py`. A scalar type is a `_ScalarAlias` of the Python type it accepts:

```python
Complex = _ScalarAlias("Complex", complex)
```

The object only has to exist so that the annotation can be evaluated when the user's module is loaded. The compiler reads annotations from the source text.

## 2. The Type Dictionary

`zinnia/compile/transformer/base.py` translates an annotation into the dictionary the core deserializes:

- `_TYPE_ALIASES` maps every accepted spelling to the canonical variant name (`"Complex"` and `"complex"` to `"Complex"`);
- `_SCALAR_TYPES` lists the variants that take no arguments, which are emitted as a bare string;
- `make_type_dict` builds the dictionary of a parameterized type, such as `{"NDArray": {"shape": [2, 3], "dtype": "Integer"}}`, and rejects malformed arguments with an `InvalidAnnotationException`.

## 3. The Core Type and Value

- Add a variant to `ZinniaType` in `src/types/zinnia_type.rs`. Its serde form must match the dictionary of step 2. Update `Display` and the predicates (`is_number`, `is_integer`, ...).
- Add a variant to `Value` in `src/types/value.rs` that holds what the compiler knows about such a value (for `Complex`, two float `ScalarValue`s), and handle it in `zinnia_type()` and `value_id()`.

The compiler then reports every exhaustive `match` on `Value` that needs a case. Many matches have a wildcard arm instead, so also search for the places that handle the closest existing variant.

## 4. Circuit Inputs

An input crosses from Python to the core as a tree of nodes (`src/circuit_input.rs`):

- `_build_input_node` in `zinnia/exec/input_parser.py` converts the Python argument into a node, for `Complex` the sequence `[real, imaginary]` of two floats;
- `read_input_value` in `src/ir_gen/helpers.rs` reads the node in the circuit with `ReadInteger`/`ReadFloat` statements at the input's path, and calls `check_input_domain` on every leaf so that the prover cannot supply a value outside the type's domain (`src/ir_gen/input_domain.rs`).

## 5. Outputs

`src/ir_gen/outputs.rs` splits a returned value into the cells it exposes on the public vector and records the output layout. A type that may be returned needs a case there (a complex number exposes its real and imaginary parts).

## 6. Merges

`helpers::value_ops::select_value` (`src/helpers/value_ops.rs`) builds the value of a name after a branch whose condition is a runtime value. Decide how two values of the new type merge, and how a value of the new type merges with values of the existing types (a complex number and a real number merge into a complex number). If no merge makes sense, reject it with a clear error.

## 7. Operations

Add the operations the type supports:

- Python operators in `apply_binary_op` and the unary operators in `src/helpers/value_ops.rs` and `IRGenerator::apply_unary_op`;
- conversions in `src/helpers/dtype.rs` if the type can be the target of `astype` or a `dtype=` argument;
- NumPy functions and methods in `src/ir_gen/named_attr/` (see [Adding Operators](/docs/contributing/adding-operators)).

Express every operation in the existing IR instructions where possible. A new instruction needs semantics in the kernel and an implementation in every backend.

## 8. Arrays of the New Type

Array cells are integers or floats (`ArrayElem` in `src/ir_array.rs`), and an array's element type is a `NumberType` (`src/types/zinnia_type.rs`). A static complex array keeps its real and imaginary parts in two float storages, and its `StaticArray` value records the second one (`imag_segment_id`). Supporting arrays of a new type means adding a `NumberType` and deciding how its elements map to cells in the array store (`src/builder/store.rs`) and in the array helpers.

## 9. Tests and Documentation

Add tests for annotations and inputs (`testing/api/test_input.py`), for operations and merges (`testing/lang/`, `testing/syntax/`), and for invalid uses that must be rejected. Describe the type in `docs-site/content/language/type-system.mdx`.
