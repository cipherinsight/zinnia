# Contributing to Zinnia

Zinnia is a Python package (`zinnia/`) with a native extension written in Rust (`src/`). The Python side reads the circuit's source and translates it into an abstract syntax tree. The Rust core generates the IR, optimizes it and proves it. Most contributions touch the Rust core.

## Development Setup

Build the extension in editable mode as described in [Installation](/docs/getting-started/installation): install the Python dependencies, then run `scripts/develop.sh`, which calls `maturin develop`; the build script links the Z3 library from the `z3-solver` wheel. Add `--release --features halo2-base-backend,noir-backend` to build the proving backends. Rebuild after every change to `src/`. Changes to `zinnia/` take effect without a rebuild.

## Running the Tests

With the virtual environment active, the Python tests under `testing/` compile and run circuits on the mock backend:

```bash
pytest                                    # all tests under testing/
pytest testing/operator/ndarray           # one directory
pytest testing/syntax/test_if.py
```

The Rust unit tests sit next to the code in `#[cfg(test)]` modules. Like the extension, they link the `libz3` of the active environment's `z3-solver` wheel:

```bash
scripts/check_tests_compile.sh            # type-check the Rust tests
cargo test --release --lib --features halo2-base-backend,noir-backend -- --skip prove::
```

The `--skip prove::` leaves out the slow tests that generate keys and proofs. `scripts/check_build_matrix.sh` checks that every combination of backend features still compiles.

## Writing Tests

A Python test defines a `@zk_circuit` function and calls it. The call compiles the circuit and runs it on the mock backend, and the result is truthy when every constraint holds:

```python
from zinnia import zk_circuit, NDArray


def test_sum():
    @zk_circuit
    def circuit(a: NDArray[int, 4], expected: int):
        assert a.sum() == expected

    assert circuit([1, 2, 3, 4], 10)
    assert not circuit([1, 2, 3, 4], 11)
```

Place tests by subject: `testing/syntax/` for Python constructs, `testing/operator/` for builtins, methods and NumPy functions, `testing/lang/` for language semantics, soundness and backend agreement, and `testing/api/` for the Python API. A change to how a value is computed should also be checked against NumPy on inputs where the branches, bounds and index wraps differ.

## Soundness

Every lowering must accept exactly the inputs that NumPy accepts and prove exactly NumPy's result. When a change drops a check, uses a prover hint, or relies on a fact, write the argument for why it is sound next to the code, as the existing constructions in `src/lower/` and passes in `src/optim/` do. A query to the resolver or Z3 that returns "unknown" must lead to the general, more expensive path, never to the cheap one.
