# Adding Optimization Passes

An optimization pass takes the IR graph and returns an equivalent one that costs less to prove. Passes are Rust types in `src/optim/` (or in `src/lower/` when they belong to the array lowering layer), and `compile_circuit_impl` in `src/lib.rs` decides which run and in what order. Read [Optimization Passes](/docs/compiler-internals/optimization-passes) first for the existing pipeline.

## The `IRPass` Trait

```rust
pub trait IRPass {
    fn exec(&self, ir_graph: IRGraph) -> IRGraph;
}
```

A pass consumes the graph and returns the new one. The graph's statements are in topological order, every statement reads only earlier ones, and passes must keep it that way.

## Before Writing a Pass

A pass may change how values are computed. It must not change which inputs the circuit accepts or which outputs it proves. In practice:

- Keep every fixed statement (`IR::is_fixed`): checks, public outputs, reads of public inputs, external calls. Removing or weakening a check needs an argument that it holds on every input that satisfies the remaining constraints, without relying on itself or on another check removed with it. Write that argument in the pass's module documentation.
- Do not remove a statement whose own constraints restrict its operands (a division's quotient window, a float operation's range) when the restriction is still needed. Several existing rewrites are deliberately not applied for this reason.
- Treat "unknown" from the resolver or Z3 as no information.
- Consider whether the rewrite belongs in an existing pass. Local algebraic rewrites usually belong in `PatternMatchOptim` (`src/optim/pattern_match_optim.rs`).

## Implementation Patterns

**Rebuild through an `IRBuilder`.** Most passes walk the statements in order and re-emit each one into a fresh `IRBuilder`, substituting values where they rewrite. The builder assigns new statement ids, keeps the order valid, and records the compile-time value of every statement whose operands are constants, which later passes and `ConstantFold` use. `DoubleNotElimination` (`src/optim/double_not_elimination.rs`) is the smallest example:

```rust
use std::collections::HashMap;

use crate::builder::IRBuilder;
use crate::ir::IRGraph;
use crate::ir_defs::IR;
use crate::types::{StmtId, Value};

use super::IRPass;

pub struct DoubleNotElimination;

impl IRPass for DoubleNotElimination {
    fn exec(&self, ir_graph: IRGraph) -> IRGraph {
        let mut builder = IRBuilder::new();
        let mut value_lookup: HashMap<StmtId, Value> = HashMap::new();
        // Maps ptr of a NOT result -> the original operand value
        let mut not_original: HashMap<StmtId, Value> = HashMap::new();

        for stmt in ir_graph.get_topological_order(false) {
            let ir_args: Vec<Value> = stmt
                .arguments
                .iter()
                .map(|&arg| value_lookup[&arg].clone())
                .collect();

            let result = if matches!(stmt.ir, IR::LogicalNot) {
                let operand = &ir_args[0];
                if let Some(ptr) = operand.stmt_id() {
                    if let Some(orig) = not_original.get(&ptr) {
                        // Double negation — eliminate
                        orig.clone()
                    } else {
                        let new_val = builder.create_ir(&stmt.ir, &ir_args);
                        if let Some(new_ptr) = new_val.stmt_id() {
                            not_original.insert(new_ptr, operand.clone());
                        }
                        new_val
                    }
                } else {
                    builder.create_ir(&stmt.ir, &ir_args)
                }
            } else {
                builder.create_ir(&stmt.ir, &ir_args)
            };

            value_lookup.insert(stmt.stmt_id, result);
        }

        let mut new_graph = builder.export_ir_graph();
        new_graph.resolver_mut().on_ir_mutated(&[]);
        new_graph
    }
}
```

The pass leaves the inner `not` in place. The dead-code elimination that runs later removes it when nothing else reads it, so a pass does not need to clean up after itself.

**Remove statements in place.** A pass that only deletes statements can collect their ids and call `IRGraph::remove_stmt_bunch`, which renumbers the rest. Every statement that reads a removed one must be removed in the same call.

**Analyze first.** `IRGraph` keeps `in_links`, `out_links` and the degree vectors, so a pass can find the consumers of a statement before deciding what to rewrite. Integer intervals come from `optim::range::RangeResolver`, and harder questions can go to `LayeredResolver` (`src/optim/resolver/`), whose Z3 queries are bounded by a deterministic step budget.

## Registering the Pass

1. Declare the module in `src/optim/mod.rs` (`mod my_pass;`) and export the type (`pub use my_pass::MyPass;`).
2. In `src/lib.rs`, import it in the `use optim::{...}` list and add an arm to `apply_pass`: `"MyPass" => MyPass.exec(graph),`.
3. Push its name at the right place in the pass list built in `compile_circuit_impl`. Ask what the pass needs and what it produces. Passes that need equal expressions to be one statement go after `DuplicateCodeElimination`. A pass that leaves unread statements is followed by `DeadCodeElimination`. A pass that reasons about array operators must decide whether it runs before `ArrayLowering`, when array operators are placeholders, or after, when they are scalar IR.

`apply_pass` restores the list of elided outputs and the provenance table after every pass, and drops provenance records whose values no longer exist, so a rebuilding pass does not have to carry them itself.

A pass that should be switchable needs a key in `OptimizationConfig` (`zinnia/config/optimization_config.py`), its value in the `optimization` dictionary that `ZinniaCompiler` sends to the core (`zinnia/compile/zinnia_compiler.py`), and a check of that key where `compile_circuit_impl` builds the list.

## Testing

Add Rust unit tests that build a small graph with `IRGraph::new` from `IRStatement::new(...)` values, run the pass, and inspect the result. `src/optim/tests/passes.rs` has examples for the existing passes. Then run the Python test suite, which compiles and runs many circuits through the whole pipeline. `ZINNIA_COMPILE_PHASE_TRACE=1` shows the statement count after each pass, and `ZKCompiledProgram.get_ir_stmts()` returns the final IR for inspection.

A pass that drops checks should also have tests with inputs that violate the dropped check's condition, to show that the circuit still rejects them.
