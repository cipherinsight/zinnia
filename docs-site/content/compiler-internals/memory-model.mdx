# Arrays and Memory

A circuit has no addressable memory: every wire is fixed when the circuit is built. A read `a[i]` at a runtime index `i` must therefore be built from constraints that work for every possible `i`, and so must a write and an operator such as `np.sort`. There are many ways to do this (a chain of selects, an inner product with a one-hot vector, a lookup in a table, a memory-consistency argument, a sorting network, a prover hint with a check), and the cheapest depends on the sizes, on how the result is used, and on the proving system.

Zinnia therefore separates *what* an array holds from *how* the circuit builds it. IR generation records array values and array operators in a compact form, and the array lowering layer (`src/lower/`) chooses the constructions after dead-code elimination, when it knows which results the program uses.

## Arrays During IR Generation

**Storages.** A *storage* is the compile-time identity of the cells that some Python names reach. An array and every view of it (a slice, a transpose, a contiguous reshape, an alias `b = a`) share one storage and address it through their own offset and strides. Storages exist only in the IR generator, in the array store of `src/builder/store.rs`. Each is in one of two states:

- `Cells`: the compiler knows every cell as a value (a statement or a constant), and no IR exists for the array as a whole;
- `Version`: after a write at a runtime position, the cells are those of an IR array version.

Every read and write goes through the store, which applies the current write predicate:

| Access | `Cells(c)` | `Version(v)` |
|---|---|---|
| read at a constant address `k` | `c[k]`, no IR | `ArrayRead(v, k)` |
| read at a runtime address `i` | `ArrayRead(ArrayInit(c), i)` | `ArrayRead(v, i)` |
| write `x` at a constant address under predicate `p` | `c[k] := select(p, x, c[k])` | `ArrayWrite(v, k, x, p)` |
| write `x` at a runtime address under `p` | `ArrayWrite(ArrayInit(c), i, x, p)`, the storage becomes `Version` | `ArrayWrite(v, i, x, p)` |

A program whose arrays are only accessed at compile-time positions therefore produces no array IR at all.

**Sharing that Zinnia does not keep.** NumPy shares memory in cases where Zinnia makes a copy: a view whose layout depends on a private value, or a name bound to one of two arrays depending on a runtime condition. The generator links such storages (`src/ir_gen/detached_copies.rs`), and a write to one makes the other *stale* (`src/builder/stale.rs`). Reading a stale array is a compile error, so the program never observes a difference from NumPy. Python lists are values in Zinnia, so mutating a list that is reachable through another binding is rejected too (`src/ir_gen/list_sharing.rs`).

**Bounded dynamic arrays.** A `DynamicNDArray` value has a storage of `max_length` cells and runtime metadata (length, rank, shape, strides and offset as scalar values) within its compile-time envelope. Its operations are in `src/ops/dyn_ndarray/`. The inputs' metadata is read with `WitnessDynamicNDArrayMeta` and checked against the envelope (see `DynamicNDArrayMetaAssertInjection` in [Optimization Passes](/docs/compiler-internals/optimization-passes)).

## Arrays in the IR

An array version is a statement whose value is a vector of `len` cells (`src/ir_array.rs`):

```
v  = ArrayInit  { len, elem }   (c_0, ..., c_{len-1})
v' = ArrayWrite (access)        (v, i_0, ..., i_{r-1}, x, p)
y  = ArrayRead  (access)        (v, i_0, ..., i_{r-1})
```

An `ArrayAccess` names the cell `offset + Σ_k i_k · stride_k`. Constant indices are folded into the offset, and each runtime position `i_k` must lie in `[0, len_k)`, otherwise there is no witness. The generator passes positions after NumPy's negative-index wrap and checks them where the access runs, so this only rejects inputs on which NumPy raises. `ArrayWrite` sets the cell to `x` where the predicate `p` is nonzero and leaves the version unchanged where it is zero. All three operations are pure. A write defines a new version and leaves the old one unchanged.

When it builds these statements, the builder applies the definitions where the operands decide them (`src/builder/arrays.rs`): a read of an `ArrayInit` at a constant address is that cell, a read of a write at an address the write cannot reach reads the older version, a read of an unconditional write at the same access is the written value, and a write under a false predicate is the old version.

## Array Operators

For operators whose element-by-element expansion is expensive, IR generation emits one `ArrayOp` placeholder statement per output element, a *lane* (`src/lower/op.rs`). All lanes of one operator instance share the operator kind and the leading operands (the inputs), and together they form a *group*. Examples are sorts and argsorts (`np.sort`, `np.argsort`, `np.median`, `np.percentile`), `np.searchsorted` on a constant table, reads at runtime indices, crops and slices with runtime bounds, the first or last set position of a flag vector, `np.insert` at a runtime position, masked writes `a[mask] = v`, permutation scatters, `np.correlate`, `np.convolve`, float matrix products and `np.corrcoef`. Dead-code elimination removes the lanes nothing reads, so `np.argsort(a)[:3]` keeps three lanes of the argsort.

## The Array Lowering Layer

`ArrayLowering` (`src/lower/emit.rs`) replaces every placeholder and every array version. It works in four steps:

1. **Groups and requirements.** Placeholders of one operator instance form a group, and each version tree (an `ArrayInit` with the versions written from it and their reads) forms a *memory group*. The things the program needs are *requirements* (`src/lower/graph.rs`): the value of each live lane, values several constructions of a group can share, and *facts* such as "`i` lies in `[0, n)` wherever this code runs".
2. **Candidates.** Every registered *construction* (the `Construction` trait in `src/lower/construction.rs`, listed by `lower::registry`) looks at each group and offers candidates. A candidate states the requirements it produces (postconditions), the facts it needs (preconditions), its cost on the compile target and an emitter. Facts that hold without any construction (interval bounds, guarantees of scalar gadgets the program emits anyway, and the definitions of operators) are *free facts* (`src/lower/facts.rs`). The program's own checks are candidates too: a check that a construction proves anyway can be dropped, and a check can justify another construction's precondition.
3. **Selection.** `src/lower/select.rs` chooses a minimum-cost set of candidates that justifies every requirement without circular justification, with Z3 and a greedy fallback. A candidate is paid once however many requirements it serves, so a value two groups share or a program-wide facility (the verifier challenge, the RAM trace) is paid once.
4. **Emission.** The selected constructions emit scalar IR, tables and memories, prover hints together with the constraints under which each hint has only one accepted value, and identity checks. A precondition that nothing establishes becomes a check emitted through `src/builder/guard.rs`.

Every construction documents its preconditions, postconditions, cost formula per target, and its soundness argument next to its code. The families are:

| Family | Code | Constructions (examples) |
|---|---|---|
| sort | `src/lower/sort/` | sorting networks, a hinted sort pinned by a permutation check (routed through a Waksman network, or a grand product at a verifier challenge), rank selectors, a sort of an input already known to be sorted; `searchsorted` by counts or a hinted position |
| gather | `src/lower/gather/` | an element by a select chain, by equality indicators or by a one-hot vector; first and last set positions by running products or a select chain; windows by a shared one-hot shift; permutation scatters |
| memory | `src/lower/memory/` | an element by the bits of its index, or by a read-only table (`RomInit`/`RomRead`); version trees as an overlay of selects, as products of keep bits for writes of zero, or as one memory (`RamInit`/`RamWrite`/`RamRead`), a shuffle-checked RAM trace on halo2-base and a native RAM block on Noir |
| scatter | `src/lower/scatter/` | `np.insert` at a runtime position; masked writes as selects or as decision lists |
| linear | `src/lower/linear/` | correlations and matrix products as direct sums, or checked as a polynomial identity or by Freivalds' check |
| stats | `src/lower/stats/` | `np.corrcoef`, by exact integer sums or a centred fixed-point computation, chosen by element type |
| permutation | `src/lower/permutation.rs` | the `is_permutation` precondition, by hit counts or a grand product |

**Verifier challenges.** Identities such as a multiset equality or a matrix product are much cheaper to check at a random point than to compute. On halo2-base the challenge is drawn after the first proof phase commits every value (`src/lower/challenge.rs`), and the check is sound except with probability `degree / |F|`. Noir has no such challenge, so these constructions are never offered on the Noir target.

## Array Facts

An *array fact* is a claim about all cells of an array value or a part of it: every element in a range, the elements non-decreasing or strictly increasing, distinct, at most `k` of them nonzero, or the array a permutation of `0..n`. The IR generator states the facts that the program's preconditions and Boolean inputs give, and derives the facts of written and merged arrays (`src/builder/array_facts.rs`, `src/optim/array_facts/`). Further facts hold by the definition of the statements (the value lanes of a sort are non-decreasing), by interval bounds, or by the program's checks. The lowering layer reads them (`IR::ArrayFact`, `src/lower/array_facts.rs`) to drop checks and to choose cheaper constructions, for example a sort of an input that is already sorted. A construction that relies on an array fact is offered only when the fact is already established, and the layer never adds a check for one, since that would reject inputs the program accepts. A fact may be stated only if a constraint enforces it wherever it is claimed to hold, or it holds by the definition of the cells. `docs/array-facts.md` has the full design.
