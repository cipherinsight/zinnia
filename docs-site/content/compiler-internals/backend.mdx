# Backends

A backend takes the compiled IR and a witness and either checks the constraints (the mock backend) or produces a zero-knowledge proof (halo2-base and Noir). All of them live in `src/prove/` and share one interpreter and one definition of the value semantics.

## Backend Names

`prove::create_prover_backend` maps a name to a backend:

| Name | Backend | Cargo feature |
|---|---|---|
| `"mock"` | `MockProverBackend`: evaluates the constraints, no proof | always built |
| `"halo2-base"` | `Halo2BaseProverBackend`: synthesizes and proves in-process with Axiom's halo2-base library | `halo2-base-backend` |
| `"noir"`, `"noir-ultrahonk"` | `NoirProverBackend`: emits a Noir program and proves it with `nargo` and `bb` (UltraHonk) | `noir-backend` |

The names `"halo2"` and `"halo2-ipa"` belonged to a retired backend and are an error that names `halo2-base` as the replacement. A backend whose feature was not compiled in is an unknown name.

The proving backend is chosen at proving time (`ZKCompiledProgram.prove(..., backend=...)`), while `ZinniaConfig.backend` is chosen at compile time and selects the *compile target* whose costs the array lowering layer minimizes: `"noir"` selects the Noir target, and the default `"halo2"` selects halo2-base. The target also decides which constructions are available. Constructions that check an identity at a verifier challenge exist only on halo2-base, so a program to be proved with Noir must be compiled with `backend="noir"`.

## Shared Pieces

**The kernel** (`src/prove/kernel.rs`) defines the value semantics: field arithmetic over BN254's scalar field, the fixed-point encoding of floats (32 fractional bits by default, `ProvingParams.precision_bits`), floor division and remainder, the polynomial approximations of the transcendental functions, the prover hints, and Poseidon. The mock backend evaluates with these functions, and the other backends constrain the same algorithms.

**Preprocessing** (`src/prove/preprocess/`) runs before every proof. It evaluates the IR with the kernel, calls the Python function of each `InvokeExternal` through the `ExternalCallback` trait (`PyExternalCallback` in `py_callback.rs`), and stores the results in the `ResolvedWitness` that the backend then reads.

**The interpreter** (`interpret_ir` in `src/prove/interpreter.rs`) walks the statements in order and calls one method of the `Synthesizer` trait (`src/prove/traits.rs`) per instruction. Each backend implements `Synthesizer` with its own cell type: a field value for the mock, an assigned cell for halo2-base, a Noir expression for Noir. The interpreter checks the RAM discipline of `src/ir_array.rs` (each memory version written at most once, each read before the write that replaces its version), skips the external-call statements that preprocessing resolved, and rejects an `ArrayOp` placeholder. `ArrayWrite` and `ArrayRead` are evaluated only by the mock, for tests of IR that has not been lowered. A proving backend receives lowered IR.

**`ProverBackend`** (`src/prove/traits.rs`) is the interface `src/lib.rs` uses: `estimate_params` sizes the circuit, `prove` and `prove_with_cached_artifact` return a `ProofArtifact`, and `verify` checks one. An artifact names its backend, carries the public values and the `ir_hash` (a BLAKE2b digest of the IR statements, `src/prove/ir_hash.rs`), so it can be verified on its own (`verify_proof_artifact`).

## Mock Backend

`src/prove/mock/` evaluates every constraint on the witness and reports whether all hold. It produces no proof: a satisfied run returns an artifact whose proof is the string `mock_satisfied`. Calling a `@zk_circuit` function runs it on this backend.

## halo2-base Backend

`src/prove/halo2_base/` builds the circuit with halo2-base's virtual-region builder, which packs the gadgets into rows automatically. `estimate_params` chooses the circuit size `k` (2^k rows) and the lookup width. An `IdentityCheck` is laid out in a second phase: every value of the first phase is committed, a challenge is drawn from the transcript, and the identity is checked at that point (`circuit.rs`, `identities.rs`). Besides `prove`, this backend registers Python functions for separate key generation and reuse (`ZKCompiledProgram.setup`, `load_keys`, `prove_with_keys`, `verify_with_keys`) and for cell statistics.

## Noir Backend

`src/prove/noir/` implements `Synthesizer` as an emitter of Noir source. It writes a package with `Nargo.toml`, `src/main.nr`, `Prover.toml` and the fixed-point library `noir_fpc` (embedded from `benchmarking/noir_fpc` with `include_str!`), runs `nargo execute`, and proves with `bb prove --scheme ultra_honk`. Verification runs `bb verify` against the public values `bb` reports. `NoirProverBackend::execute` runs the program without proving, which the differential tests use to compare Noir's results with the mock backend's.

## Witness Independence

The circuit a backend builds must not depend on the witness: the verifier rebuilds it without one. `emit_structural_circuit` in `src/lib.rs` renders a structural form of the circuit (the Noir source, or a halo2-base cell fingerprint, also without any witness) for a given witness, and `testing/lang/test_witness_independence.py` checks that two witnesses give identical renderings.
