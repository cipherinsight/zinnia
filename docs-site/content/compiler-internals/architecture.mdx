# Compiler Architecture

This page follows one circuit through the compiler. The Python package prepares the source and translates it into a JSON abstract syntax tree (AST). The Rust core generates the IR, optimizes it, lowers its array operators, and later proves it.

## Pipeline Overview

```
@zk_circuit function
    |  zinnia/compile/lowering/        source rewrites (imports, helpers, callbacks)
    v
lowered Python source
    |  zinnia/compile/transformer/     Python ast -> JSON AST dict
    v
AST + config + chips + externals (JSON)
    |  src/lib.rs: compile_circuit
    v
IRGenerator (src/ir_gen/)            symbolic execution -> IRGraph
    |
    v
pass pipeline (src/optim/, src/lower/)  -> optimized, lowered IRGraph
    |
    v
CompiledIR handle (held by ZKCompiledProgram)
    |  src/lib.rs: prove_circuit
    v
preprocess (src/prove/preprocess/)   external calls, resolved witness
    |
    v
backend (src/prove/)                 mock | halo2-base | noir
```

## The Python Side

### Decorators

`@zk_circuit` (`zinnia/api/zk_circuit.py`) reads the function's source when the module is loaded, but compiles nothing yet. Calling the decorated function creates a `ZKCircuit`, collects the `@zk_chip` and `@zk_external` functions visible from the module and from the caller's locals, compiles, and runs the circuit on the mock backend. `ZKCircuit.compile()` returns a `ZKCompiledProgram` (`zinnia/api/zk_compiled_program.py`), whose `prove`, `verify` and `serialize` methods call into the Rust core.

### Source Lowering

`zinnia/compile/lowering/` rewrites the Python source before translation. Its module docstring lists the steps in order. In short:

- module-level imports other than `numpy` and `math` are rejected when the function uses them, and names imported from those two modules are spelled `np.` and `math.`;
- reads of module-level literal constants are replaced by the literals;
- nested functions, lambdas and function aliases become generated chips that take their captured variables as arguments;
- `map`, `filter`, `np.vectorize`, `np.piecewise`, `np.apply_along_axis` and `np.fromiter` become calls of generated chips;
- `for` loops over `zip` and `reversed` are desugared into index loops.

Each rewrite keeps Python's meaning or rejects the program with an error naming the construct.

### AST Transformer

`ZinniaCircuitASTTransformer` (`zinnia/compile/transformer/circuit.py`, with the shared visitor in `base.py`) walks Python's `ast` and returns a plain dictionary: the circuit's parameters with their type annotations and privacy (public or private), its preconditions (`requires`, parsed in `_precondition.py`), and its body. `ZinniaChipASTTransformer` (`chip.py`) and `ZinniaExternalFuncASTTransformer` (`external_func.py`) do the same for chips and external functions. The transformer also rejects Python syntax the compiler does not support.

### The Call into Rust

`ZinniaCompiler.compile` (`zinnia/compile/zinnia_compiler.py`) serializes four JSON payloads, the AST, the configuration (backend, `loop_limit`, `recursion_limit`, and the optimization switches of `OptimizationConfig`), the chips and the externals, and calls `compile_circuit` from `zinnia._zinnia_core` (re-exported by `zinnia/compile/_bridge.py`). The result is an opaque `CompiledIR` handle. The IR stays in Rust memory; `export_ir_json` and `import_ir_json` serialize it when a program is saved or loaded.

## The Rust Core

### Entry Point

`compile_circuit` in `src/lib.rs` runs `compile_circuit_impl` on a dedicated thread with a large stack, because IR generation and several passes recurse deeply. `compile_circuit_impl` reads the configuration, runs IR generation, builds the pass list, and runs it.

### IR Generation

`IRGenerator::generate_from_json_with_chips` (`src/ir_gen/mod.rs`) deserializes the AST into the types of `src/ast/mod.rs` and visits it. The generator owns two pieces of state:

- `IRContext` (`src/ir_ctx.rs`): the stack of scopes (`src/scope.rs`) that maps names to values and records the branch, loop, return and chip-entry conditions;
- `IRBuilder` (`src/builder.rs` and `src/builder/`): appends IR statements, computes the compile-time value of each statement where its operands are known, keeps the array store, the fact stack and the provenance table, and emits every check under the current execution predicate.

Statements are visited in `src/ir_gen/visitors.rs`. Calls (`f(...)`, `np.f(...)`, `x.method(...)`) are dispatched in `src/ir_gen/named_attr/`, which calls the implementations in `src/helpers/` and `src/ops/`. Circuit inputs are read in `src/ir_gen/helpers.rs`, each with a domain check (`src/ir_gen/input_domain.rs`). The outputs and their layout on the public vector are built in `src/ir_gen/outputs.rs`. [Symbolic Execution](/docs/compiler-internals/symbolic-execution) describes this step.

### Optimization and Lowering

`compile_circuit_impl` builds the list of pass names and `run_pass_pipeline` applies them through `apply_pass`. Some passes depend on the `OptimizationConfig` switches. The array lowering pass (`lower::ArrayLowering`) always runs, because no backend accepts the array placeholders it replaces. Its constructions are priced on a compile *target* chosen from the configured backend name (`Target::from_backend`): `"noir"` selects the Noir cost model and every other name selects halo2-base. [Optimization Passes](/docs/compiler-internals/optimization-passes) lists the pipeline.

After the pipeline, `compile_circuit_impl` places the output layout recorded during IR generation on the optimized graph's public vector and returns the `CompiledIR`.

### Proving

`prove_circuit` in `src/lib.rs` creates the requested backend (`prove::create_prover_backend`), estimates its parameters unless they are given, runs preprocessing (`src/prove/preprocess/`), which calls the Python callables of external functions and builds the resolved witness, and then proves. `verify_proof_artifact` checks a proof artifact with the backend named in it. [Backends](/docs/compiler-internals/backend) describes the three backends.

## Errors

The AST transformer raises subclasses of `InternalZinniaException` (`zinnia/debug/exception/`) that carry the source location, and `ZKCircuit.compile` turns them into a `ZinniaException` whose message shows the offending source line (`zinnia/debug/prettifier.py`). The Rust core reports errors as `ValueError`, `RuntimeError` or a Rust panic, and `ZKCircuit.compile` converts each into a `ZinniaException` with the core's message.

## Diagnostics

A few environment variables help when working on the core:

| Variable | Effect |
|---|---|
| `ZINNIA_COMPILE_PHASE_TRACE=1` | prints the time and statement count after IR generation and after each pass |
| `ZINNIA_LAYER_INPUT=<path>` | appends the IR that the array lowering layer receives to `<path>` |
| `ZINNIA_SMT_ENABLE=0` | answers compile-time constant queries without range analysis or Z3 |
| `ZINNIA_SMT_LOG_TELEMETRY=1` | prints a summary of the constant-resolution queries at the end of compilation |

The measurement switches (`ZINNIA_ABLATE_*`, `ZINNIA_FORCE_CONSTRUCTION`, `ZINNIA_LAYER_REPORT`) are documented in `docs/ablations.md`.
