# Symbolic Execution

IR generation (`src/ir_gen/`) runs the circuit function once, over symbolic values instead of concrete ones. Each value is either a compile-time constant or the result of an IR statement. The output is a straight-line list of IR statements: one circuit that is correct for every input. This page explains how each kind of control flow is compiled and how the generator decides what it knows at compile time.

## State of the Generator

The `IRGenerator` holds:

- **The scopes** (`IRContext` in `src/ir_ctx.rs`, scope kinds in `src/scope.rs`): the circuit scope, chip scopes for inlined calls, conditional scopes, loop scopes and generator scopes for comprehensions. A scope maps names to values and records the condition under which its code runs (the branch condition, the loop's not-broken condition, the not-yet-returned condition, a chip's entry condition).
- **The builder** (`IRBuilder` in `src/builder.rs`): appends statements and computes each statement's compile-time value when its operands are constants (`build_value`). It also holds the *fact stack*, the facts that hold at the current point (path conditions, preconditions, asserted comparisons), and the array store described in [Arrays and Memory](/docs/compiler-internals/memory-model).

The **execution predicate** of a statement is the conjunction of the conditions of all scopes it is in. It is true exactly on the inputs for which Python would execute the statement. Before compiling each statement, the generator sets the builder's *write predicate* to this predicate. Every write and every check the builder emits uses it.

## Branches

`visit_branches` in `src/ir_gen/visitors.rs` compiles `if c: A else: B`:

1. If the builder already knows `c` as a constant, only the arm it selects is compiled, and that arm's bindings become the bindings after the `if`.
2. Otherwise both arms are compiled, `A` in a scope whose condition is `c` and `B` in one whose condition is `not c`. Each arm also pushes its path condition on the fact stack, so code in the arm can use it.
3. After the arms, a name assigned in both arms is bound to `select(c, value_A, value_B)` (`merge_binding`). A name assigned in only one arm that existed before the `if` already holds the merged value, because the assignment itself merged with the old value under the arm's predicate. A name first bound inside one arm of a runtime branch stays local to that arm.

Selects of structured values are built by `helpers::value_ops::select_value`, element by element for lists, tuples and arrays (see [Types and Values](/docs/compiler-internals/type-inference) for how differing types and shapes are joined). Each arm is compiled once, so the cost of nested branches is the sum of their arms instead of one copy per path.

## Loops

Every loop is unrolled.

- **`for` loops and comprehensions** (`src/ir_gen/iteration.rs`). When the number of items is a compile-time constant, the body is compiled once per item. When the trip count is a runtime value (`range(n)` with a private `n`, or the length of a bounded dynamic array), the loop is unrolled to a proven upper bound and each item gets an *activity condition*. Inactive items run under a false predicate, so their writes change nothing and their assertions hold vacuously. For a runtime-bounded `range`, the circuit also asserts that the item after the last unrolled one is inactive, so a bound that was inferred too small makes the circuit unsatisfiable instead of truncating the loop. A loop with no provable bound is rejected, as is a runtime-bounded `range` whose proven bound exceeds 2^24 items.
- **`while` loops** (`visit_while`). A loop that counts a variable to a bound with one `i += c` is unrolled like the equivalent `range`. Any other `while` loop is unrolled one iteration at a time, with the guard as the iteration's condition, until the guard is a constant false or the resolver (below) proves it false. When a proof rather than a constant ended the unrolling, the circuit asserts that the guard is false where the loop is still running, so a wrong proof makes the circuit unsatisfiable instead of dropping iterations. If the guard is not proved false within `loop_limit` iterations (`ZinniaConfig`, default 1000), compilation fails.
- **`break` and `continue`** add conditions to the loop scope (`Scope::loop_break`, `Scope::loop_continue`), so the rest of the body and later iterations run under their negation.

A name first bound inside a loop body that the loop may leave before the assignment is bound only on some paths. `src/ir_gen/unbound_names.rs` asserts at each read that one of its assignments ran, so no proof exists for an input on which Python would raise `UnboundLocalError`.

## Returns

A `return` registers its value together with the current predicate (`IRContext::register_return`), and later statements run under the condition that no return has happened. At the end of the function, the registered values are merged with selects. For the circuit function itself, the merged value becomes the output (`src/ir_gen/outputs.rs`).

## Function Calls

A call of a `@zk_chip` function is inlined (`visit_chip_call` in `src/ir_gen/chip_external.rs`). The body is compiled in a chip scope whose entry condition is the caller's predicate, so writes, assertions and returns inside the body stay predicated on the call happening. A recursive call is inlined only while the condition under which it is reached may hold, and a call that is not proved unreachable within `recursion_limit` nested calls (default 16) is rejected.

A call of a `@zk_external` function is not compiled. It emits `ExportExternalI`/`ExportExternalF` statements for the arguments and an `InvokeExternal` statement, and its result is read with `ReadExternalResult`. The Python function runs during preprocessing, before proving, and its result enters the circuit as a value the prover supplies. Nothing relates the result to the arguments unless the program asserts it.

## Checks

Python raises `IndexError`, `ZeroDivisionError` or a math-domain error only on the paths it executes. The circuit must be satisfiable on the other paths, so every check the generator emits goes through `src/builder/guard.rs`, which emits the check `c` as `p → c` for the current execution predicate `p`. An `assert` statement compiles to `Assert(select(p, c, true))`. An operation whose operand has an implicit domain (an index, a divisor) receives a *guarded operand* `select(p, x, s)` with a safe constant `s`, so its constraints can be satisfied where the code does not run. Nothing is emitted where the code never runs or where `p` already implies `c`.

The checks the generator adds on its own include:

- the domain check of every input element (`src/ir_gen/input_domain.rs`): integers and floats in the signed 64-bit window, Booleans in `{0, 1}`;
- index bounds of runtime-indexed reads and writes, after NumPy's negative-index wrap;
- the preconditions of the circuit (`@requires`, `src/ir_gen/preconditions.rs`), which are asserted and also recorded as facts.

## What Is Known at Compile Time

Many decisions need a compile-time number: a loop bound, a shape, an index that selects a wire directly, a branch that can be skipped. The generator gets one in three tiers:

1. **Static values.** The builder computes the value of every statement whose operands are constants, so `Value::int_val()` and `bool_val()` answer immediately.
2. **Intervals.** `optim::range::RangeResolver` propagates integer intervals forward over the statements that define a value.
3. **SMT.** `optim::resolver::SmtResolver` encodes those statements, together with the facts that hold at this point, as a Z3 query (`src/optim/smt_encoding.rs`).

`LayeredResolver::range_then_smt` chains the last two and is installed when SMT is enabled (the default, switched off by `ZINNIA_SMT_ENABLE=0`). Callers go through the helpers in `src/optim/resolver/` (`require_static_int`, `resolve_int_or_bounded`, ...), which report a uniform error when a value is not static. Each Z3 query is bounded by a budget of solver steps (`src/optim/z3_budget.rs`) instead of a wall-clock timeout, so the same source always compiles to the same circuit. An answer of "unknown" is never treated as "proved": the generator then takes the general path, which emits more constraints but no wrong ones.
