# Types and Values

The IR generator computes types while it executes the program symbolically. There is no separate type-checking pass: every expression evaluates to a `Value` (`src/types/value.rs`), and a value's type is determined by its variant. A name can therefore hold values of different types at different points of the program, and its type after a branch is the type of the merged value. The types live in `src/types/`.

## Annotation Types

The AST transformer translates each parameter annotation into a type dictionary (`make_type_dict` in `zinnia/compile/transformer/base.py`), which the core deserializes as a `ZinniaType` (`src/types/zinnia_type.rs`):

| `ZinniaType` | From annotations such as | Meaning |
|---|---|---|
| `Integer` | `int`, `Integer`, and also `bool`, `Boolean` | a signed 64-bit integer; a Boolean annotation sets a flag that adds the check `x ∈ {0, 1}` |
| `Float` | `float`, `Float` | a fixed-point number with 32 fractional bits |
| `Complex` | `complex`, `Complex` | a pair of floats (real, imaginary) |
| `NDArray { shape, dtype }` | `NDArray[int, 3, 4]` | an array of fixed shape |
| `DynamicNDArray { dtype, max_length, max_rank, max_shape }` | `DynamicNDArray[int, 8, 1]` | an array whose shape is a runtime value within a compile-time envelope |
| `SymbolicNDArray { shape, dtype, bindings }` | array annotations whose dimensions are names or bounded names | resolved before IR generation, see below |
| `List`, `Tuple` | `List[int, int]`, `Tuple[...]` | fixed-length sequences with per-element types |
| `PoseidonHashed { dtype }` | `PoseidonHashed[...]` | an input committed by its Poseidon hash |
| `String`, `None`, `Class` | | values that only exist at compile time |

The element type of an array (`NumberType`) is `Integer`, `Float` or `Complex`. NumPy's `bool` arrays are stored as integer arrays with cells 0 and 1, and the builder records which cells and storages hold NumPy bools (`src/builder/bool_dtype.rs`), because indexing with a bool array and with an integer array mean different things.

A `SymbolicNDArray` is resolved when the circuit's inputs are read (`resolve_shape_type` in `src/ir_gen/mod.rs`): a dimension whose symbol has a binding, or an exact value implied by the preconditions, becomes fixed, and one with only an upper bound becomes runtime-sized. The input is then an `NDArray` when every dimension is fixed and a `DynamicNDArray` otherwise.

## Values

`Value` combines the type with what the compiler knows about the value:

- `Integer`, `Float`, `Boolean`: a `ScalarValue` with an optional compile-time value (`static_val`) and the statement that computes it (`stmt_id`). A constant needs no statement until an operation uses it.
- `Complex { real, imag }`: two float scalars.
- `StaticArray`: an array of fixed shape. It carries its element type, shape, strides and offset, and the id of its *storage* (the field `segment_id`), the compile-time identity of the cells it shares with its views.
- `DynamicNDArray`: an array of runtime shape, with its envelope (`src/types/envelope.rs`: per-axis bounds and dimension variables that record which dimensions are equal) and its runtime metadata (length, shape, strides and offset as scalar values).
- `List`, `Tuple`: Python sequences, holding their element values.
- `String`, `None`, `Class`: compile-time only.

Every value also has a `ValueId`, its identity for facts and provenance records. A clone is the same value and keeps it.

## Types at Operations

Binary operations dispatch on their operand variants (`helpers::value_ops::apply_binary_op`, and `ops::dispatch_binary_numeric` for the scalar NumPy functions):

- integer and Boolean operands use the integer instruction, and a Boolean is read as 0 or 1;
- if either operand is a float, the integer operand is converted with `FloatCast` and the float instruction is used;
- a complex operand promotes the other one to complex, and the operation is computed on the parts;
- array operands are broadcast by NumPy's rules and the operation is applied per element.

Comparisons return Booleans. Conversions requested by the program (`astype`, `np.int64(x)`, the `dtype=` argument) go through `src/helpers/dtype.rs`, which follows NumPy's casting. NumPy's fixed-width integer types (`np.uint8`, `np.int16`, ...) produce values in the type's range. Zinnia's values do not carry such a type and are computed in 64 bits, so arithmetic on these values and assignment into arrays of these types are rejected (`src/builder/fixed_width.rs`).

## Types at Joins

After a branch, a loop item that may be inactive, or a function with several `return`s, the value of a name is `select(c, a, b)` built by `helpers::value_ops::select_value`:

| `a` and `b` | Merged value |
|---|---|
| a constant condition | `a` or `b`, without IR |
| two integers or Booleans | `SelectI` (a NumPy bool when both sides are) |
| an integer and a float, or two floats | `SelectF`, the integer side converted to float |
| a complex number and a number | a complex number, each part selected |
| two arrays of the same shape and element type | an array of per-cell selects |
| two 1-D arrays of different lengths, or a fixed-shape and a runtime-shaped array | a runtime-shaped array whose metadata is selected as well |
| two multi-dimensional arrays of different shapes, or an array and a number | a stand-in that is an error to read (`merge_of_different_shapes` in `src/ir_gen/detached_copies.rs`): the program compiles only if it rebinds the name before using it |
| lists or tuples of one length | element-wise merge |

## Errors

Type errors are reported during IR generation, at the operation that cannot be built: an operation that does not accept its operand types, a shape that cannot be broadcast, a shape or bound that cannot be resolved to a compile-time number, or a read of a merged name whose possible values have incompatible shapes.
