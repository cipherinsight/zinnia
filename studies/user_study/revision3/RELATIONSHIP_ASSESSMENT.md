# 数组关系复杂度与 Rust 实现评估

本评估检查当前 revision 3 的六道题，不修改已运行的研究页面、任务定义或参与者记录。比较对象是当前准备好的 Rust/ndarray 0.16.1/RISC Zero 环境与 Zinnia 数组前端，不是对所有 Rust 库或全部 RISC Zero 工作流的结论。

## 实际验证

为每题实现了 3–5 种合理的 Rust 解法，共 **22 种**。全部在 RISC Zero 中通过同一套 3 个公开示例和 9 个隐藏用例，共 **264 个正确性检查**。其中包括完整广播/归约方案，而不只是循环较多的写法。

另构造了 **13 个有明确错误机制的程序**：全部通过 Rust 编译，其中 12 个被当前公开测试发现；1 个通过全部公开示例，在隐藏的小尺寸网格上运行失败。这些是人为构造的诊断探针，不是参与者数据，也不是错误发生率的估计。

还验证了三个对应的 Zinnia 数组表达式：越界切片终点的截断、空内部区域切片、转置后的 reshape，均通过公开及隐藏用例。另一个 API 探针确认当前 ndarray 的三维数组不能直接调用批量 `.dot()`；这是编译期 API 使用障碍，不能与编译后计算错误混为一谈。

完整程序：[rust_relationship_audit.py](rust_relationship_audit.py)。机器可读结果：[rust-relationship-audit.json](rust-relationship-audit.json)。这些程序通过临时沙箱验证，不会触碰真实参与者数据。

## 逐题判断

| 题目 | 已验证的 Rust 实现 | 可能增加的关系维护负担 | 作为组间差异的候选强度 |
|---|---|---|---|
| 1. 批次校准和能量 | 逐通道迭代器、广播/归约、纯循环 | `[B,C]` 参数插入时间轴；时间归约后保留批次和通道 | 较弱到中等：Rust 也有直接且紧凑的广播解法，双方都要选择正确的轴 |
| 2. 不等通道数交叉乘积 | 分批 dot、广播外积再归约、纯循环 | 独立中心化、共同时间轴、矩形 `[B,C,D]` 输出 | 中等：分批 dot 增加批次/输出管理；完整广播可以显著缩小差异 |
| 3. 投影后的加权距离 | 分批 dot 后逐点、投影后广播、完全广播、直接投影点差的循环 | `D→F` 投影、`N×M` 配对、批次权重、不同归约轴的连续切换 | 较强候选：多个相互关联的中间形状；但不能忽略 Rust 的完全广播方案 |
| 4. 跨步膨胀滤波 | 标量累加、区块乘积、按偏移 dot、先降采样再滤波 | 输出大小、窗口起点、采样间距、切片边界、输入/输出通道 | 当前为中等且存在设计弱点：stride=dilation=2 可以消去一层关系 |
| 5. 矩形区块协方差 | 显式收集六个像素后 dot、stack/归约/dot、纯循环、reshape/转置/复制、完整广播外积 | 空间轴分组、六像素观测轴、双通道输出轴、转置视图的布局 | 较强候选：形状之外还有布局关系；不同 Rust 写法确有不同的易错点 |
| 6. 批次掩码扩散 | 逐单元向量 dot、空间切片后 dot、纯循环 | 批次掩码、通道混合方向、同步轮次、冻结单元、空内部区域 | 中等到较强：切片方案有已复现的边界差异；同步更新错误并非 Rust 独有 |

“候选强度”是对机制的判断，不是观测到的组间效应大小。

## 三个可复现的具体机制

### 1. 动态轴关系不在 ndarray 的静态类型中

`Array3<i64>` 表示三维数组，不表示某一维是 B、N 或 F，也不保证两个参数的批次数/通道数匹配。把 `[B,C,D]` 错分配成 `[B,C,C]`，或者在投影结果上用 D 而不是 F 作循环上界，都能通过编译，随后才出现错误值或形状/索引 panic。

NumPy 也不会检查轴的语义。可能的优势是 `@`、`einsum` 等操作可以直接表达收缩和批次关系，减少用户在多个位置重复维护尺寸。它不意味着 Python 循环天然更安全。

### 2. 切片容错语义不同

膨胀窗口的 Python 写法 `x[..., start:start+2*U:2, ...]` 在末端会自动截断；只要实际选出的索引正确，这就是合法实现。直接对应到 Rust ndarray 的 `start..start+2*U;2`，末端超出数组长度时会 panic。通过 RISC Zero 复现了 `assertion failed: end <= axis_len`。

扩散题的 Rust 空间切片方案省去小网格保护后，公开示例全部通过，隐藏的 `H=1,W=2` 输入失败，诊断为 `start <= axis_len`。对应的 Zinnia 空切片表达式无需这个保护即可通过。这说明有具体的接口差异，但纯循环 Rust 解法本身能自然跳过无内部单元的网格。

### 3. 转置后 reshape 的布局处理不同

Zinnia/NumPy 的分组写法使用 `reshape → transpose → reshape`。对应的 Rust 视图在转置后直接 `.into_shape_with_order(...).unwrap()`，复现了 `ShapeError/IncompatibleLayout`。先做 `.as_standard_layout().to_owned()` 再 reshape 的正确版本通过全部测试。

Rust 的显式像素收集或 stack 方案可以绕开这条风险路径，因此该差异依赖实现策略，不能推断所有 Rust 实现都易错。

## 已发现的任务设计弱点

滤波题目前 stride 和 dilation 都是 2。以下合法方案已在 RISC Zero 验证通过：先取 `x.slice(s![..,..;2,..;2,..])`，随后在降采样图像上执行普通的无填充滤波。它不需要分别维护输出步长和滤波器膨胀率。两参数相等也使“把两者混淆”的错误难以被识别。

下一版可把两者改成不同值，例如 stride=2、dilation=3，并继续验证所有自然实现。这个建议尚未修改现场任务。

## 对下一轮 pilot 的建议

优先观察第 3、5 题，第 6 题作为补充，第 1 题保留为相对简单的参照。保留 Rust 的广播、矩阵运算、视图和辅助函数写法，不能用强制循环人为增加难度。

现有公开测试会发现本次 13 个错误探针中的 12 个，所以更有解释力的指标是首次尝试正确性、从错误到正确所需的有效时间、尝试次数，以及编译错误/运行时关系错误/错误数值的分类；最终提交正确率可能继续接近。

完整 attempt trail 可以测量这些结果。真实错误发生率仍应在控制 NumPy/ndarray 熟悉度的后续 pilot 中观察，不能由本次人为构造的错误程序估算。
